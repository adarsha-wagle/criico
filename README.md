# Criico

A cricket club register: players, teams, match scorecards and an Impact Score leaderboard.
Admins record and edit data; viewers can browse everything.

## Tech stack

| Area             | Choice                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------- |
| Framework        | Next.js 16 (App Router, Turbopack, `cacheComponents`, React Compiler)                    |
| UI               | React 19, Tailwind CSS 4, shadcn/ui on Base UI, lucide and Phosphor icons, sonner toasts |
| Database         | Neon Postgres via `@neondatabase/serverless`                                             |
| ORM / migrations | Drizzle ORM, drizzle-kit                                                                 |
| Validation       | Zod 4, shared by forms, Server Actions and API routes                                    |
| Auth             | Custom JWT (`jose`, HS256) in an httpOnly cookie, passwords hashed with `bcryptjs`       |
| Tests            | Vitest                                                                                   |
| Language         | TypeScript (strict)                                                                      |

## Getting started

### Prerequisites

- Node.js 20.9 or newer
- A Postgres database (the project is set up for Neon)

### 1. Install

```bash
npm install
```

### 2. Environment variables

Create `.env` in the project root:

```bash
DATABASE_URL=postgres://...            # pooled connection string, used by the app
DATABASE_URL_UNPOOLED=postgres://...   # direct connection, used by scripts (optional)
JWT_SECRET=at-least-32-random-characters
MAX_AGE_SECONDS=604800                 # session length (7 days)
AUTH_COOKIE=token                      # cookie name (optional, defaults to "token")
```

`src/config/env.ts` validates these at startup and fails fast if one is missing or too short.

### 3. Create the tables

```bash
npm run db:migrate
```

### 4. Create an admin

New sign-ups are viewers. Admins are created (or existing users promoted) with:

```bash
npm run create-admin -- admin@criico.com "a-strong-password" "Admin"
```

### 5. Seed demo data (optional)

Adds the 2025 Nepal Premier League teams with five players each. Stats are demo numbers.

```bash
npm run db:seed              # add anything missing, safe to re-run
npm run db:seed -- --reset   # wipe matches, players and teams first (users are kept)
```

### 6. Run

```bash
npm run dev       # http://localhost:3000
```

## Folder structure

The app uses a **feature-based design**. Each feature (players, teams, matches, leaderboard)
lives in its own route folder and keeps the code only it uses next to its pages:
`_components` for its UI and `_actions` for its Server Actions. The leading underscore keeps
these folders out of the URL. Code shared by several features lives in `src/components` and
`src/lib`.


### API routes

Every handler checks the session itself (middleware does not cover `/api`). Responses use one
envelope: `{ isError, statusCode, message, data }` on success and
`{ isError, statusCode, message, errors? }` on failure.

| Method | Route                | Access    | Purpose                                       |
| ------ | -------------------- | --------- | --------------------------------------------- |
| POST   | `/api/auth/register` | Public    | Create a viewer account and log in            |
| POST   | `/api/auth/login`    | Public    | Log in, sets the session cookie               |
| POST   | `/api/auth/logout`   | Public    | Clear the session cookie                      |
| GET    | `/api/leaderboard`   | Signed in | Leaderboard, optional `?role=` and `?limit=`  |
| GET    | `/api/players`       | Signed in | All players, optional `?role=`                |
| POST   | `/api/players`       | Admin     | Create a player                               |
| GET    | `/api/players/[id]`  | Signed in | One player                                    |
| PATCH  | `/api/players/[id]`  | Admin     | Update a player                               |
| GET    | `/api/matches`       | Signed in | Recent matches                                |
| POST   | `/api/matches`       | Admin     | Record a match and update player totals       |
| GET    | `/api/matches/[id]`  | Signed in | One match with performances                   |
| PATCH  | `/api/matches/[id]`  | Admin     | Replace a match and recalculate player totals |

## Server Components and Server Actions

### React Server Components

Every `page.tsx` and layout is a Server Component. They read the database directly through
`src/lib/queries` (no fetch to the app's own API), and anything that reads cookies or the
database sits inside `<Suspense>`, as `cacheComponents` requires.

| Page                                  | Server-side data                                                      |
| ------------------------------------- | --------------------------------------------------------------------- |
| `/`                                   | Top five from `getLeaderboard`, session for the header links          |
| `/dashboard` (layout)                 | Signed-in user for the user panel (`getUserById`)                     |
| `/dashboard`                          | `getDashboardStats`                                                   |
| `/dashboard/leaderboard`              | `getLeaderboard` with the role filter from `searchParams`             |
| `/dashboard/players`                  | Players joined with their team, Impact Score worked out on the server |
| `/dashboard/players/new`, `[id]/edit` | Admin check, team options, the player being edited                    |
| `/dashboard/teams`                    | `listTeams` (squad size and record)                                   |
| `/dashboard/teams/[id]/edit`          | `getTeamById` with its squad                                          |
| `/dashboard/matches`                  | `listMatches`                                                         |
| `/dashboard/matches/[id]`             | `getMatchById` scorecard                                              |
| `/dashboard/matches/new`, `[id]/edit` | Roster with team ids, team options, saved match values                |

Client Components (`"use client"`) are kept to the parts that need interactivity: the login,
register, player, team and match forms, the dashboard nav and the logout button.

### Server Actions

| Action file                                    | Actions                                    | Used by                                                                |
| ---------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------- |
| `dashboard/players/_actions/players-action.ts` | `createPlayerAction`, `updatePlayerAction` | Player form (`/dashboard/players/new`, `/dashboard/players/[id]/edit`) |
| `dashboard/teams/_actions/teams-action.ts`     | `createTeamAction`, `updateTeamAction`     | Team form (`/dashboard/teams/new`, `/dashboard/teams/[id]/edit`)       |

The forms call them through `useActionState`. Each action checks the session and admin role,
validates with Zod, writes to the database, then calls `revalidatePath`. Expected problems
(validation, duplicate names) come back as state and show as a toast plus inline errors.
`createTeamAction` inserts the team and then its squad with the new team id in one transaction.

The match form posts JSON to `/api/matches` instead, because its performance rows are dynamic.
Login, register and logout also go through the API routes.

## Auth flow

1. **Register**: `POST /api/auth/register` validates the input, hashes the password with
   bcrypt and creates the user with the `viewer` role. The new user is logged in straight away.
2. **Log in**: `POST /api/auth/login` checks the password (bcrypt runs even for unknown emails,
   so both failures look the same) and signs a JWT with `jose`: HS256, subject = user id, role
   claim, expiry = `MAX_AGE_SECONDS`.
3. **Cookie**: the token is stored in an httpOnly, `SameSite=Lax` cookie (`Secure` in
   production), so client-side JavaScript can't read it.
4. **Middleware** (`src/middleware.ts`) verifies the cookie on `/dashboard/*` and the auth pages:
   - no valid session on a dashboard page: redirect to `/auth/login?from=<path>`, and delete an
     expired or tampered cookie
   - already signed in on login or register: redirect to `/dashboard`
   - after login the user goes back to `from`, but only if it points inside the site
5. **Server checks**: middleware is not the only guard. API routes call `requireSession()`
   (401 when signed out, 403 for non-admin writes), Server Actions check the session and role
   themselves, and admin-only pages show an "Admins only" state to viewers.
6. **Log out**: `POST /api/auth/logout` deletes the cookie and the client redirects to
   `/auth/login`.

Roles: **viewer** can see everything; **admin** can also add and edit players, teams and
matches. Admins are made with `npm run create-admin`.

## Impact Score

Defined in `src/lib/impact-score.ts`, weights in `src/config/constant.ts`, tests in
`src/lib/impact-score.test.ts`.

- Base score: `runs x 1.2 + wickets x 20`
- Batsman: runs x 1.3 before the base weight; Bowler: wickets x 1.5 before the base weight
- Wicketkeeper: +30 flat, and can never get the Bowler multiplier (enforced by its type)
- Fewer than 5 matches: -50 (rookie); more than 20 matches: +100 (veteran)

## Data rules

- Players belong to at most one team. A match side can only list players from the team picked
  for it, checked in the form and again on the server.
- A match result must agree with the scorecard: the winner must have more runs, and a draw needs
  equal runs. Otherwise the form refuses to submit and the API returns 400.
- Recording a match adds each performance to the player's career totals in one transaction;
  editing a match first subtracts the old performances, so nothing is counted twice.
